# ADR 0002: The Lean infoview is ProofLens's first surface

- Status: accepted
- Date: 2026-08-24
- Applies to: `lean/ProofLens/Widget.lean`, `lean/widget/src/`, `apps/web/`, `packages/renderer-svg/`

## Context

ProofLens has to be looked at somewhere. The obvious choice, and the one the
original specification assumed, was a local web application: TypeScript, React,
Vite, SVG, served on localhost.

The alternative is to render inside the Lean infoview. Lean 4 ships a user
widget system: a constant annotated `@[widget_module]` carries a JavaScript ES
module, and a command can attach it to a syntax node with
`Lean.Widget.savePanelWidgetInfo`. The infoview supplies React through an import
map and renders the module's default export as a panel next to the code.
[ProofWidgets4](https://github.com/leanprover-community/ProofWidgets4) is a
community toolkit built on the same mechanism, and mathlib already depends on it.

## Decision

**Ship the infoview widget first. The web application is a second consumer of
the same VisualIR, not the primary product.**

Use Lean core's `@[widget_module]` directly rather than depending on
ProofWidgets4. ProofWidgets4 is a helper layer over the core mechanism; taking
it on would add a version-pinning relationship and a release-fetching build step
for functionality ProofLens does not yet need. Its `Html` and RPC helpers become
worth adopting when ProofLens wants interactive round-trips to Lean, which is a
v0.2+ question.

## Why

**The reader is already there.** People who work with Lean have the infoview
open. A separate web application asks them to export JSON, start a second
process, and switch windows — three steps between a theorem and its
interpretation, each of which is a place to give up.

**Provenance gets better, not just cheaper.** Invariant 2 says a user should be
able to click a visual element and learn why ProofLens is showing it. Inside the
editor, the declaration is elaborated by the same frontend that is checking the
file. Source positions are live, the environment is current, and the pretty
printer is fully configured — which, as ADR 0001 records, is not a given
outside the frontend. The provenance path is short and real rather than
reconstructed from a snapshot.

**Renderer independence makes it nearly free.** Invariant 7 already required
that visual reasoning and visual rendering be separable. Because renderers
consume VisualIR and nothing else, the widget is just another consumer. The
entire deterministic pipeline — Formal IR, MathIR, classification, planning,
SVG — is TypeScript with no Node-specific dependencies, so it runs unchanged in
the infoview's JavaScript context. The Lean side of the widget does exactly one
thing: hand over Formal IR as widget props.

That last point is the architectural payoff. There is no ProofLens server, no
analysis API, and no second implementation. The CLI, the web application, and
the widget run byte-identical analysis code.

## The related decision: what the demo leads with

The same reasoning changed what v0.1 is *about*.

The specification's headline example was a plot of an upper bound. But a plot of
`x ≤ P / T` is schematic — it can show which side of a line a quantity lies on
and nothing more — and it tells a working mathematician nothing they did not
already read in the statement.

Assumption sensitivity is different. Computing which stated hypotheses the proof
term actually references is an `Expr` traversal, it is `derived` rather than
guessed, and its output is a fact a reader could not get by looking at the
statement. On ProofLens's own corpus it immediately found that
`information_rate_bound` states `0 < P` and never uses it — a real observation
about a real theorem, surfaced without anyone looking for it. It is also
directly on mission: machine-generated proofs accumulate hypotheses that do no
work, and nothing in the existing Lean tooling surfaces that well.

So the planner leads with assumption sensitivity whenever there is something to
report, and the bound plots are supporting material. An author's
`@prooflens.visual` hint can reorder figures but never displaces a finding: a
preference is taste, a redundant hypothesis is information.

## Consequences

- The widget bundle is committed to the repository at
  `lean/ProofLens/Widget/prooflens.js` and inlined with `include_str`, so
  `lake build` works without a Node toolchain. It is regenerated by
  `pnpm build:widget` and CI checks that the committed copy is current.
- `react`, `react-dom`, and `@leanprover/infoview` are marked external in the
  esbuild config. Bundling React would give the widget a different React
  instance than its host and break hooks.
- Widget extraction is scoped: `Extract/Focus.lean` extracts the target
  declaration plus its same-module dependency closure, which is enough for a
  useful local dependency graph without paying to extract an entire module.
- The web application remains supported and is the right surface for the
  audience that does not use Lean — the "here is an unfamiliar machine-generated
  theorem, what does it mean?" reader in the north-star. That audience does not
  exist in volume yet, which is exactly why it is not the v0.1 priority.
- ProofLens is now coupled to Lean's widget API, which is stable but not frozen.
  The coupling is confined to one 40-line file.
